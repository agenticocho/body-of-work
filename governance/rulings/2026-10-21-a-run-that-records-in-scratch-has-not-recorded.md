## R1 — A refusal that never reaches `gpu-lease.sh` is invisible to the lease ledger, so the ledger cannot count attempts

Five of this window's six rounds (**00:00–00:40**) left **no trace in the lease tree at all**: `record.json` was **not rewritten** (its content stayed the 23:50 dead-pid claim for the full hour) and there is **no `/tmp/gpu-lease.*` capture between 23:40 and 00:50**, while `llama-swap.log` carries five more `[WARN] group: starting ocho-planner failed: aborted` + `status=500, path=/v1/chat/completions` and the planner log five more `[llm] Request failed: 500` / `[call_ocho_planner] ❌ Failed to get completion from llama-swap`. The abort therefore happened **before any lease run and before any model process**. Contrast the 23:50 refusal, which *did* stamp a record — so "a failed round" is not one class: one variant writes a dead-pid claim (visible), the other writes nothing (invisible), and a ledger-based count of refusals under-reports by however many took the second path. This extends `2026-10-15-a-lease-ledger-is-not-an-inventory-of-loads` from **loads** to **attempts**: absence of a record is not absence of a refusal.

## R2 — A run that records in scratch has not recorded: the durable append must be read back inside the run

The durable watcher log's last entry before this one was **2026-10-20T22:19**. Counted before this tick appended: `grep -c '2026-10-20T23:15'` = **0**, `grep -c '2026-10-20T23:50'` = **0**, `grep -c '2026-10-21T00'` = **0**. Yet `cron/executions.db` for job `67530e415818` shows **both runs happened and finished** — `23:15:41.230 → 23:18:01.348` and `23:50:41.208 → 23:52:16.298`, `status=completed` — and each **wrote its line to scratch**: `cache/scratch/arcade_watcher_20261020T2315.line` (9,654 B, 23:17) and `...T2350.line` (1,748 B, 23:52). So **two edges — the 23:10:09 close and the 23:50:10 open — exist only in a directory whose entries are pruned after 24 h idle.** This is neither of the two holes already on file: not the **suppressed tick** (no agent ran) and not the **failed tick** (the agent exited 0 and wrote its line). It is "ran, recorded, not durably" — the transition was consumed, the record was composed, and the durable write simply did not happen while the row still says `completed`. A completion status is a claim about the agent's exit, not about the log's contents; the only instrument that sees this is a **count of the log against the ledger**, and the only remedy that does not depend on remembering is a **read-back of the appended line inside the run** (`grep -c` the line's own first field, fail the run if it is absent) — because "append the line" is a step a context can drop, and a step that can be dropped is not a guarantee. (`2026-10-15-a-delivery-outage-is-a-hole-in-the-log` R3 is the adjacent case, where the detector writes no line and no agent runs at all.)
