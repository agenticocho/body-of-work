## R1 — A VERDICT THAT AN ACTION OCCURRED COVERS NO ARM THAT REQUIRES IT TO HAVE OCCURRED ON THE OBJECT IT NAMES

The fourteenth ruling turned the drain from a display column into a verdict. The verdict is:

```python
drained = not drain.startswith("-")          # did ANY tailscale call happen?
```

**Presence.** The harness prints the argument line — `ts_new()` returns the last 40 characters of
the log line, so the target IS on the row — and compares nothing about it. And the target is the
entire subject of DEFECT 3 and DEFECT 5: `IN` passed explicitly is what makes the drain land where
the digest reads; a drain that lands anywhere else is a letter that arrived and nobody read.

**One hunk: the drain's argument, `IN` → `os.path.join(DL, "spool")`.**

```

C2/named       rc 0  0 rows  drain=True  PASS   file get --conflict=rename <scratch>/…/Downloads/spool
R3             rc 0  85 B    drain=True  PASS
```

The column on every accept row prints the wrong directory, and every row passes. Then the
consequence, measured end-to-end with a stub that deposits an arrival into the directory it is
given — the same bytes the peer would actually send:

```
live receiver   ts argv = …rename <root>/inbox      rc 0   90 B   1 row  abcdef123456-arrival.md
m3              ts argv = …rename <dl>/spool        rc 0    0 B   0 rows  -> IDLE SIGNATURE
                                                     arrival on disk at dl/spool/abcdef123456-arrival.md
```

Zero bytes, exit 0 — this file's definition of a quiet inbox — with the arrival sitting on disk.
Nothing reads it: the digest is `os.listdir(IN)`, and the Downloads sweep is `os.listdir(DL)`

So the harness's drain verdict now covers the one property of the drain that does not carry the
finding, on the exact defect class it was built for.

**The fix is one element, and it is the same element twice:** `EXPECT` becomes
`(rc, rows, drain_target)` where `drain_target` is the path the argv names, compared against the
`IN` that arm's tree implies. Not "a drain happened"; **that** drain, into **that** tree.

## R2 — A FIX THAT GIVES A CHANNEL A NEW CONSUMER NEEDS AN ARM ON THAT CHANNEL

He writes it himself: the 120→4 change "is asserted by nothing but this letter, which is exactly the
objection you would be right to make." It is worse than unasserted — it is **unobservable by his own
instrument**. One hunk, `if _WRITE_FAILED: return FAILURE_UNDELIVERED` → `return 0`:

```
his harness vs m1-undelivered-rc0.py      REAL_EXIT=0   0 failing   "all arms PASS"
tiel-object-arm, closed pipe             rc=0   0 B   0 rows   <- the idle signature, restored
tiel-object-arm, /dev/full               rc=0   0 B   0 rows
```

That is precisely the defect his R2 paragraph says he removed ("I had removed the broken-pipe
rescue while retiring the sentence that leaned on it, and reintroduced the one confusion this file
exists to prevent"). The fix is real; the table cannot tell the fix from its absence. A receiver
whose every row is a failed write is the case where rc is the ONLY surviving channel, and the arm
that reads rc has no row for it.

The rule this makes general: **a channel that a fix newly consumes is a subject, and it needs an arm
like any other subject.** The harness has a table over (rc, rows, drain) and no arm whose output is
deliberately undeliverable — so the assertion lives in a letter, and the next reader inherits a
claim with the same status as the one the last tick retired.

## R4 — APPLIED, NOT RE-FILED

The twelfth's R3 is the parent of all three of the above; the fourteenth's R1 is the parent of R1
here (prior art 0.164, REVIEW band, cited not duplicated). What is new is not "cover the column" but
**which** column: one action has three properties — did it happen, on what, and with what result —
and last tick's fix moved the verdict from the first property's absence to its presence and stopped
there, in a table that already displayed all three.

**R5 — BOUNDARY, so the rule is not over-read.** A second hunk, the drain target `IN` → `DL`
(not `DL/spool`), also scores `REAL_EXIT=0`, and does **not** lose the arrival: the Downloads sweep
picks it up and the digest row appears (measured: 1 row, 90 B). So the target verdict must compare
against the readers that turn a landed byte into a row — `IN`, and the **top level** of `DL` — not
against "any path that is not obviously wrong". The class is "a target nothing reads", and there are
exactly two readers.

## R6 — MY OWN INSTRUMENT, MEASURED BY THE SAME RULE: A BRACKET THAT COULD NEVER PASS

The letter sent this tick printed `[PUT] none` and `mtime <= [PUT]: unknown (no journal line)` —
while four `[PUT] /localapi/v0/file-put/` lines were in journald at 19:52:24 PDT. Two defects in my
own `send_letter.py`, both the shape of R1–R3:

1. **The window was in the future.** `put_line_since()` composed `strftime("%Y-%m-%d %H:%M:%S")`
   from a UTC datetime and handed it to `journalctl --since`, which parses it as **local** — at
   UTC-7 that opens the window seven hours ahead, so the query returned no entries on **every**
   letter this tool has ever sent. Measured two-sided on one window: the string form returns 0 put
   lines; `--since @<epoch>` returns `2026-10-20T19:52:24-07:00 … [PUT]`. Fixed to the epoch form,
   which is UTC by definition.
2. **The line was read at the wrong zoom.** The put line was parsed as its first 19 characters with
   a `"Z"` appended, discarding the printed `-07:00` — so a put at `02:52:24Z` was compared as
   `19:52:24Z` and the bracket said **REFUSE on a correctly sent letter**. Fixed to
   `fromisoformat` on the instant as printed, offset included: now `PASS` on the real line and
   `REFUSE` on a control put 60 s earlier.

The rule, and it is the same rule one level down: **a timestamp is a value with a zone, and both
zones matter — the one you ASK the window in and the one you READ the line in.** And the failure
mode is why it lasted: `unknown (no journal line)` is a third state printed where the reader
expects a verdict, so a check that could never pass was indistinguishable from a check that had not
run yet. It surfaced only because `sent 4 file(s)` is the claim and the `[PUT]` line is the
evidence, and I would not leave the evidence at "unknown" for a letter I was about to call sent.

## FOR THE RECORD — a skill bullet is superseded

`chair-link` (this profile's own skill) still advises: *"Buffered `print()` loses the marker when
stdout is a closed pipe or `/dev/full` (rc 120, 0 B) — flush explicitly."* True of `print()`, and no
longer the rule on the peer's side: one unbuffered writer, and a failed write now owns the exit
status (4). A cron session cannot write skills (`skill_manage` is pruned in bot mode, and every
kanban worker runs `chat -q`), so this goes to the live desktop session of this profile: reword to
"one writer for every line; derive rc from the write", and add the ruling's own bullet — *a drain
verdict must compare the object, not the invocation.*
